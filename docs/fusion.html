Fusion モードの仕組み

YamabikoChat（iOS / Android）に実装されている Fusion は、複数の LLM を並列実行し、 専用の「ジャッジ」モデルで回答を比較・分析したうえで、最終回答を合成するマルチモデル・オーケストレーションです。

iOS + Android Panel → Judge → Synthesizer プリセット: quality / budget / fast / custom トレース保存

1. 概要 — Fusion とは何か

通常のチャットは 1 つのモデルがユーザーに直接答えます。Fusion モードでは、 同じ質問を 複数のパネルモデル に独立して投げ、それぞれの回答を ジャッジモデル が構造化 JSON で比較し、最後に シンセサイザー（合成）モデル がユーザー向けの最終回答を書き上げます。

設計上の狙い:

  • 単一モデルの盲点やハルシネーションを、複数視点の比較で緩和する
  • 合意点・矛盾点・独自の洞察を明示的に整理してから最終回答を作る
  • 各フェーズのレイテンシ・コスト・成否を FusionTrace として記録する
プラットフォーム: Fusion は iOS（ios/YamabikoChat/Features/Fusion/）と Android（app/.../data/fusion/ + ui/fusion/）の両方に実装されています。プロンプトとデフォルトプリセットは両プラットフォームで一致させています。

フェーズ 役割 実行方式 主な実装

4. プリセットとモデル構成

プリセットは ios/YamabikoChat/App/Resources/FusionPresets.json にバンドルされています。 設定画面で custom を選ぶと、ユーザー定義の JSON（最大 4 パネル）を使えます。

プリセット 用途 パネル数 タイムアウト Web 検索
quality 高精度リサーチ（デフォルト） 4（Gemini Pro, Claude, GPT-4.1, DeepSeek） 120s 可
budget コスト抑制 3（Flash 系中心） 60s 不可
fast コーディング向け高速 2（Flash + DeepSeek） 30s 不可
custom ユーザー編集 1〜4 プリセット定義に依存 設定に依存

各プリセットは次のスロットを持ちます:

  • panelModels[] — 並列実行する分析パネル（role はジャッジ用ラベル）
  • judgeModel — 比較・構造化分析
  • synthesizerModel — 最終回答の執筆
  • fallbackModel — 障害時の単一モデル（省略時は synthesizer と同値に正規化）

タスク種別（FusionTaskType）は research / coding / auto。 auto のときはプリセット内の taskType をそのまま使い、パネル用システムプロンプトの付録が切り替わります。

5. チャット送信時のデータフロー

ユーザーが Fusion モードでメッセージを送ったときの流れ（ChatRepository.sendFusionMessage）:

  1. 前提チェック — isFusionModeEnabled が true であること。
  2. ユーザーメッセージ保存 — DB に role=user で挿入。
  3. リクエスト構築 — FusionPresetLoader.buildRequest で会話の system prompt・設定・カスタム JSON を反映。
  4. 会話履歴取得 — パネルフェーズでは履歴 + 今回のユーザー入力（添付ファイル含む）を渡す。
  5. Judge まで実行 — fusionService.runThroughJudge（Panel 並列 → Judge）。この間 UI は「Fusion 分析中…」表示。
  6. トークン記録 — 各パネル・ジャッジの usage を fusion_panel_* / fusion_judge として記録。
  7. アシスタントメッセージ枠作成 — 空テキストで挿入し、fusionTraceId を紐付け。
  8. シンセサイザーをストリーム — ChatStreamSession で逐次表示・DB 更新。
  9. トレース確定 — finalizeTrace 後、FusionTraceStore.save。
再生成不可: Fusion モード有効時は canRegenerateLastAssistant が false になり、最後のアシスタント応答の再生成はできません。

6. ジャッジの JSON 分析

ジャッジモデルは次のスキーマに沿った JSON のみを返すよう指示されます（FusionPrompts.judgeJSONSchema）:

  • consensus — 複数パネルで一致した点
  • contradictions — トピックごとの対立と解決の見込み
  • unique_insights — 特定モデルだけが持つ洞察（最終回答に使うかフラグ付き）
  • coverage_gaps — どの観点が欠けているか
  • suspected_errors — 疑わしい主張と理由
  • strongest_answer_parts — 特に質の高い部分
  • recommended_final_position — 推奨する最終立場（ユーザー向け文ではない）
  • confidence — low / medium / high

パース処理:

  1. モデル出力から { ... } 部分を抽出（markdown フェンス除去）
  2. JudgeAnalysisDTO として snake_case デコード
  3. 失敗時は jsonRepairPrompt で修復リクエストを 1 回送信
  4. それでも失敗した場合、シンセサイザーはジャッジなしプロンプト（生パネルのみ）で動作

シンセサイザーのシステムプロンプトは fusionDebugModeEnabled で切り替わります。 デバッグ ON ではモデル名の参照が許可され、OFF では内部実装をユーザーに見せない文体が求められます。

7. フォールバックとエラー処理

状況 挙動 トレース status
一部パネルのみ成功 成功分だけでジャッジ・合成を続行。失敗モデル ID は failedModels に記録。 completed または synthesis_fallback
全パネル失敗 FusionError.allPanelsFailed → fallbackModel で通常のツール付き単一ターン。 all_panels_failed
シンセサイザーのストリーム失敗 staticFallbackAnswer（ジャッジ推奨位置 or 合意 or 最速パネル出力）を DB に書き込み。 synthesis_fallback
fusionDepth >= 1（再帰防止） フル Fusion をスキップし fallback モデルへ直接（無限ネスト防止）。 recursion_fallback
個別 API タイムアウト 該当パネル／ジャッジを失敗扱い（FusionTimeout）。 （上記いずれかに帰着）

staticFallbackAnswer の組み立て優先順位: (1) ジャッジの recommendedFinalPosition → (2) consensus の結合 → (3) 生のジャッジ JSON → (4) レイテンシ最小の成功パネル全文

AppSettings の Fusion 関連フィールド

フィールド意味

fusionDebugModeEnabledデバッグ UI・シンセサイザープロンプト切替

fusionCustomPresetJSONcustom プリセットの JSON 本体

モード排他（normalizedForPersistence）

Dual モード・自動会話・Fusion は同時に有効化できません。 いずれかを ON にすると他は自動で OFF になります。設定 UI でも相互にトグルが無効化されます。

UI の触れ方

  • 設定 → 「Fusion モード」セクション（FusionModeSettingsSection）
  • チャット画面のコンポーザーにプリセット名・パネル数・分析中ステータス表示
  • デバッグ ON 時、Fusion 応答メッセージから FusionDebugSheet でトレース閲覧
  • Siri / ショートカット: RunFusionIntent（アプリ外から単発実行、debug パラメータあり）

9. トレースとデバッグ

各 Fusion 実行は UUID の requestId を持ち、SQLite の fusion_traces テーブルに JSON 全文として保存されます。 アシスタントメッセージの fusionTraceId から参照できます。

FusionTrace に含まれる主な情報:

  • 全 panelResults（成功/失敗、本文、レイテンシ、トークン、コスト）
  • judgeResult（解析 JSON、パース成否、修復の有無）
  • synthesisResult（最終合成、フォールバック使用フラグ）
  • 合計レイテンシ・コスト、failedModels、status

保存時に DiagnosticsLogger（category: fusion）へサマリも出力されるため、 アプリ内診断画面から問題調査がしやすくなっています。

まとめ

Fusion は「複数の専門家が並列で意見を出し、審判が整理し、編集者がユーザー向けにまとめる」という 人間のレビュー会議に近いパターンを LLM パイプラインで実装した機能です。 コード上は FusionOrchestrator がフェーズ制御の中心となり、 ChatRepository がチャット UX（ストリーム・永続化）と接続しています。
